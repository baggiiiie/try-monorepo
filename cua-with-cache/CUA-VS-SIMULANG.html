Backend decision · Outlook triage

Prefer CUA Driver today. Preserve Simulang.

Both backends can support the same cached API. CUA Driver is currently the practical choice because it has completed bounded live Outlook extraction and gives Pi both AX structure and screenshot context. All-Inbox completion remains unproven.

Recommendation: continue the first complete Outlook workflow on CUA Driver. Keep Simulang as an experimental backend for applications whose accessibility trees it can see reliably.
PRIMARY NOW

CUA Driver

  • Has opened and extracted real Outlook messages.
  • Provides serializable AX snapshots for bounded Pi grounding.
  • Can include a screenshot when AX structure is incomplete.
  • Fits the Stagehand-style compile-and-replay boundary.
PRESERVE

Simulang

  • Offers elegant node methods such as activate().
  • Has useful native primitives such as scoredSearch.
  • Can perform clean accessibility actions when the AX tree is healthy.
  • Can see Outlook's message list, but DFS can cycle before reaching it; breadth-first traversal works.

The architecture should stay backend-independent

Agent-authored workflows should only call the small cached API. CUA descriptors, Simulang nodes, physical input, retries, and self-healing stay inside the library. That lets us improve or replace the backend without rewriting the Outlook workflow.

Current decision: CUA-first product development, Simulang preserved—not removed.
