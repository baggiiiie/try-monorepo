# Architecture Deepening — Open Findings

Generated by the `improve-codebase-architecture` skill. Vocabulary follows
`.agents/skills/improve-codebase-architecture/LANGUAGE.md`:

- **Module** — interface + implementation
- **Deep / Shallow** — leverage at the interface vs. interface near as
  complex as the implementation
- **Seam** — where an interface lives; behaviour swap-point
- **Adapter** — concrete thing satisfying an interface at a seam
- **Locality** — change/bugs/knowledge concentrated in one place
- **Deletion test** — would deleting this module concentrate complexity
  (it earned its keep) or just move it (it's a pass-through)?

## #2 Push/LWW reconciliation — three near-copies of "last-write-wins per record"

**Files**: [`server/internal/service/sync.go`](../server/internal/service/sync.go) — `pushCategory`, `pushExpense`, `pushRecurringExpense` (~290 lines combined)

**Problem**
All three repeat the same shape:

```
GetXIncludingDeleted
  ├─ if NotFound: create + maybe soft-delete
  └─ else: compare UpdatedAt → branch on DeletedAt → maybe re-fetch
```

The actual business rule — *"server applies LWW when client `UpdatedAt` >
server `UpdatedAt`; equal-timestamps tie-break on state"* — is written
three times, each with subtly different control flow. **Deletion test**:
removing any single `pushX` would concentrate logic into the one rule
that's currently hidden across three methods.

**Solution sketch**
Name the concept (e.g. `Reconciler`) and give it a single deep interface:

```go
type Reconciler[Existing, Incoming any] interface {
    Load(ctx, q, id) (Existing, bool, error)        // bool = found
    EqualState(existing, incoming) bool
    Apply(ctx, q, action ReconcileAction, ...)
}

type ReconcileAction int
const (
    ReconcileNoOp ReconcileAction = iota
    ReconcileCreate
    ReconcileUpdate
    ReconcileSoftDelete
)
```

A single `Reconcile` function picks the action; each entity becomes an
adapter implementing the four hooks. The category-by-name reconciliation
in `pushCategory` becomes its own labelled step at this seam — it's
currently a hidden subtlety.

**Benefits**
- **Locality** — the LWW rule (and its quirks like equal-timestamp
  tie-break) lives in one place. Today, fixing a sync edge case means
  reading three sibling methods to find which has the bug.
- **Leverage** — every new sync-able entity gets LWW for free.
- **Test surface** — reconciliation can be unit-tested without SQLite.

**Open questions**
- Does the category-by-name reconciliation stay inside the adapter
  (`pushCategory` is special) or get hoisted into the `Reconciler`
  interface? Probably stays in the adapter.
- Are there enough entities (3) to justify a generic abstraction, or is
  shared free functions enough?
- The "re-fetch after write" pattern: needed because sqlc returns the
  inserted row but updates don't return rows. Could a deeper repository
  helper paper over that?

**ADR conflicts**: none currently recorded.

## #3 Partial updates leak into the API as broken zero-value semantics

**Files**:
- [`server/internal/api/expenses.go`](../server/internal/api/expenses.go) — `updateExpense`
- [`server/internal/service/expense.go`](../server/internal/service/expense.go) — `Update`
- [`server/internal/service/category.go`](../server/internal/service/category.go) — `Update` (parallel pattern)

**Problem**
The HTTP layer decodes nullable `*T` pointers, then *flattens* them into
a zero-valued `ExpenseInput`. The service then treats every empty string
or zero as "don't change". **A client cannot intentionally clear
`description` or `merchant`.** This is a textbook **shallow** module:
its semantics are leakier than its type signature suggests, and the bug
is only visible if you read both layers.

```go
// api/expenses.go
input := service.ExpenseInput{}
if req.Description != nil {
    input.Description = *req.Description  // empty string?
}
// service/expense.go
description := existing.Description
if input.Description != "" {           // <-- empty == "don't change"
    description = input.Description
}
```

**Solution sketch**
Introduce explicit patch types:

```go
type ExpensePatch struct {
    Amount      *int64
    Currency    *string
    CategoryID  *string
    Description *string  // nil = unchanged; &"" = clear
    Merchant    *string
    Date        *int64
}

func (s *ExpenseService) Patch(ctx, id string, p ExpensePatch) (*Expense, error)
```

Or `sql.Null`-like wrappers. The HTTP layer hands the patch through
unchanged; the rule "what does it mean to omit a field?" lives in *one*
place (the patch type's documentation).

**Benefits**
- **Locality** — semantics stop being split between API and service.
- **Test surface** — pass a patch with one explicit `nil`, assert the
  row is unchanged. Untestable today through the public interface.
- **Correctness** — the "clear merchant" case actually works.

**Open questions**
- CLI `expense edit` also passes through `ExpenseInput` with the same
  zero-value semantics ([`server/internal/cli/edit.go`](../server/internal/cli/edit.go)).
  Patch type unifies all three callers (CLI, API, sync) or just two?
- Do we want a generic `Patch[T]` machinery, or one patch struct per
  entity? Probably the latter — the entities are few and stable.

## #4 API ↔ service error contract is string-matched

**Files**:
- [`server/internal/api/expenses.go`](../server/internal/api/expenses.go) lines 76, 120
- [`server/internal/api/categories.go`](../server/internal/api/categories.go) — parallel cases

**Problem**
The HTTP layer maps `err.Error() == "expense not found"` to 404:

```go
if err.Error() == "expense not found" {
    writeError(w, r, http.StatusNotFound, err.Error())
    return
}
writeError(w, r, http.StatusInternalServerError, err.Error())
```

Reword the service message and the API silently regresses to 500. The
**interface** between service and API has hidden state (the literal
string); the type signature lies.

**Solution sketch**
Sentinel errors or a typed error implementing `HTTPStatus()`:

```go
// service/errors.go
var (
    ErrExpenseNotFound  = errors.New("expense not found")
    ErrCategoryNotFound = errors.New("category not found")
    ErrInvalidInput     = errors.New("invalid input")
)
```

API switches on `errors.Is`. Service-layer call sites use
`fmt.Errorf("%w: ...", ErrExpenseNotFound, ...)` for context.

**Benefits**
- **Compile-time safety** at a real seam.
- API tests can assert on sentinel without depending on prose.
- **Leverage** scales: every new not-found case reuses the contract.

**Open questions**
- Pure sentinel errors, or a typed error with explicit `HTTPStatus()`?
  The latter avoids API knowing about every service sentinel; the former
  is simpler and matches Go idioms.
- This should be a precondition for #3 (Patch types will throw new
  errors that need consistent wiring).

## #5 iOS sync apply — three near-copies of mark-synced and upsert

**File**: [`ios/ExpenseTracker/Services/SyncRepository.swift`](../ios/ExpenseTracker/Services/SyncRepository.swift) — `markCategorySynced` / `markExpenseSynced` / `markRecurringExpenseSynced`, plus the three `upsertX` methods

**Problem**
Same shape repeated per entity. Adding a new sync-able client model
requires copy-pasting six methods. The shared rule
("apply pull = upsert with `syncStatus = synced`"; "apply push response =
update timestamps + sync_status") has no name.

**Solution sketch**
A `Syncable` protocol or a generic `applyPull<R: Syncable>` /
`applyPush<R: Syncable>`. Each model declares how to upsert and how to
project the server row.

```swift
protocol SyncableRecord {
    static var tableName: String { get }
    init(from server: ServerProjection)
    func markSyncedSQL() -> (String, [DatabaseValueConvertible])
}
```

**Benefits** — mirror of #2 on the iOS side.

**Open questions**
- Server entity #2 (push/LWW reconciler) and this iOS deepening are
  *symmetric*. Do them together so the shared "syncable entity" concept
  is named consistently across both codebases? Or independently?
- Swift's protocol-with-associated-types ergonomics may push toward
  free functions instead of a protocol.

## #6 Recurring-expense materialization — domain logic buried in free functions

**File**: [`server/internal/service/recurring.go`](../server/internal/service/recurring.go) — `materializeDueRecurringExpenses`, `materializeRecurringExpense`, `nextRunDate`, `clampDay`, `startOfDay`

**Problem**
Materialization is called from `SyncService.Pull/Push` and from
`RecurringService.MaterializeDue` as a free function taking
`*dbsqlc.Queries`. The schedule logic — next-run computation,
day-of-month clamping, 120-iteration guard — is real domain (the
*Recurrence schedule*) but it's not a **module**, it's a pile of free
functions sharing a package. Pure schedule math (`nextRunDate`,
`clampDay`) is testable, but bugs hide in *how it's driven against the
DB* (the loop, the guard, the `today` cutoff) — exactly the "extracted
for testability but real bugs hide elsewhere" anti-pattern from
LANGUAGE.md.

**Solution sketch**
Promote *Recurrence schedule* to a deep module:

```go
type Schedule struct {
    Frequency   string
    DayOfMonth  *int64
    StartDate   int64
    EndDate     *int64
    NextRunDate int64
    LastRunDate *int64
}

func (s Schedule) Occurrences(after, until time.Time, location *time.Location) []time.Time
```

The materializer becomes a thin orchestrator that walks `Occurrences`
and writes rows. Sync no longer reaches into a free function.

**Benefits**
- **Test surface** = `Schedule` interface. Property tests for clamping,
  leap-year, timezone become trivial.
- **Locality** — the 120-iteration guard and "today" cutoff stop being
  magic numbers in a free function.
- The *Recurrence schedule* concept gets a name. Worth adding to
  `CONTEXT.md` (which doesn't exist yet — would be created lazily).

**Open questions**
- Should `Schedule` know about timezones, or take `*time.Location` as
  arg? The latter keeps it pure.
- Is the 120-iteration guard a real safety net or dead code?
